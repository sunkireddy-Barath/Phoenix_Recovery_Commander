Security Vulnerabilities

BUG-001 Unauthenticated Credential Endpoint Exposes Active Agent Permissions Critical
Location
backend/routes/credentials.js : 80
Description
The GET /api/credentials/active/:agentId route has no requireAuth middleware. Any anonymous HTTP client can query the active delegation credential for any agent, including its full permission list, credential ID, issuer name, and expiry. Every other credential route (/, /revoke, /audit, /issue) is guarded; this one was missed.
Vulnerable Code
// No requireAuth — open to anonymous callers
router.get('/active/:agentId', (req, res) => {   // ← line 80
  const cred = db.prepare(
    `SELECT * FROM delegation_credentials
     WHERE agent_id = ? AND status = 'active' AND expires_at > ?
     ORDER BY issued_at DESC LIMIT 1`
  ).get(req.params.agentId, new Date().toISOString());
  ...
  res.json({ credential: cred, permissions: perms });  // full details leaked
});
Impact
Attacker learns exact permission list for any agent without logging in. Enables targeted attacks: craft requests that exploit only authorized actions.
Fix
Add requireAuth as second argument: router.get('/active/:agentId', requireAuth, (req, res) => {…})
Reproduce
# No session cookie needed — returns full credential JSON
curl -s http://localhost:3001/api/credentials/active/phoenix-port-01 | python3 -m json.tool
BUG-002 All Incident Routes Lack Authentication — Anyone Can Cancel Active Incidents Critical
Location
backend/routes/incident.js : 34, 122, 129, 147, 165, 181
Description
None of the six incident route handlers use requireAuth middleware. This means an anonymous caller can: list all active incidents, read their full status (including audit trails and telemetry), cancel any running incident, and start new incidents that consume server resources. In a production plant, an adversary could cancel an active cooling-system recovery mid-execution.
Unguarded Routes
router.post('/start', async (req, res) => {       // line 34  — no auth
router.get('/status/:id', (req, res) => {         // line 122 — no auth
router.post('/cancel', (req, res) => {            // line 129 — no auth
router.get('/active', (_req, res) => {            // line 147 — no auth
router.get('/audit-trail/:id', (req, res) => {   // line 165 — no auth
router.get('/scenarios', (_req, res) => {         // line 181 — no auth
Impact
Anonymous adversary can cancel active recovery operations, enumerate all incident state, start denial-of-service incidents (up to 5 concurrent allowed), and read full audit trails.
Fix
Import requireAuth in incident.js and add it to all six route definitions. The /scenarios GET may be left public for display purposes only.
Reproduce
# List all active incidents without any session
curl -s http://localhost:3001/api/incident/active

# Start an incident without login

  -H "Content-Type: application/json" \

# Cancel it immediately (copy incidentId from above response)

  -H "Content-Type: application/json" \
  -d '{"incidentId":"<incidentId from above>"}'
BUG-003 T3N Delegation Check Fails Open — Security Bypass on API Error Critical
Location
backend/agent/t3nClient.js : 353–370
Description
In live mode, when the T3N /v1/vc/issuer/credentials/proof API call fails (network error, 429, 5xx), the catch block silently falls back to the local AUTHORIZED_ACTIONS list and returns authorized: true for those actions. This is intentional for demo uptime, but it constitutes a security bypass: a temporary T3N outage allows every "authorized" action to proceed without any on-chain delegation verification. The entire point of T3N is defeated when the verification can be trivially bypassed by disrupting the API.
Vulnerable Code
} catch (err) {
  console.warn('T3N delegation proof failed, using local fallback:', err.message);
  // Fail-open with simulation so demo is uninterrupted  ← security bypass
  const authorized = AUTHORIZED_ACTIONS.includes(action);
  return {
    authorized,         // ← always true for listed actions, even without T3N proof
    ...
    fallback: true,
  };
}
Impact
An attacker who can disrupt T3N connectivity (DNS poisoning, BGP hijack, firewall rule) removes the on-chain delegation check entirely. Agent executes "authorized" actions with no verifiable proof.
Fix
In production mode, fail closed: return { authorized: false, reason: 'T3N unavailable' } so the action is escalated to human approval rather than proceeding unverified.
Reproduce
# Set a T3N_API_KEY (any non-empty value triggers live mode)
# then point T3N_BASE_URL to an unreachable host
T3N_API_KEY=fake T3N_BASE_URL=http://127.0.0.1:1 node backend/server.js

# Start an incident — delegation check will "fail open" and still execute
curl -s -X POST http://localhost:3001/api/incident/start \
  -H "Content-Type: application/json" \
  -d '{"scenarioId":"INC-001"}'

# Observe t3nOperations[].status = "AUTHORIZED" even though T3N is unreachable
BUG-004 Hardcoded Session Secret Fallback — Sessions Forgeable in Production Critical
Location
backend/server.js : 36–37
Description
The session secret falls back to the literal string 'phoenix-secret-change-me' when SESSION_SECRET is absent from the environment. Any developer who forgets to set the env var ships to production with a known, public secret. An attacker who knows this string can forge valid session cookies and impersonate any authority level. Additionally, session cookies have no secure: true flag, so they are transmitted in cleartext over HTTP connections.
Vulnerable Code
app.use(session({
  secret: process.env.SESSION_SECRET || 'phoenix-secret-change-me',  // line 37
  cookie: {
    httpOnly: true,
    sameSite: 'lax',
    // secure: true is MISSING — cookies sent over plain HTTP
    maxAge: 7 * 24 * 60 * 60 * 1000
  }
}));
Impact
Production deployment without SESSION_SECRET set allows session forgery, full authority impersonation (LEVEL_3 harbor master), and credential issuance for any agent.
Fix
Throw on startup if SESSION_SECRET is not set and NODE_ENV is production. Add secure: process.env.NODE_ENV === 'production' to the cookie config.
Reproduce
# 1. Start backend WITHOUT SESSION_SECRET
# 2. Login normally, note the connect.sid cookie value
# 3. Decode and re-sign a forged session with the known secret:
node -e "
const cookieSignature = require('cookie-signature');
const forgedPayload = JSON.stringify({ authorityId: 'harbor_master' });
const b64 = Buffer.from(forgedPayload).toString('base64');
const sig = cookieSignature.sign('s:' + b64, 'phoenix-secret-change-me');
console.log('Forged cookie:', sig);
"
# 4. Use that cookie value in subsequent requests
BUG-005 Unknown Scenario IDs Default-Allow All Actions (Permission Fail-Open) High
Location
backend/middleware/checkPermission.js : 18–19
Description
When checkCredentialPermission receives a scenarioId not present in SCENARIO_AGENT_MAP, it returns { permitted: true } unconditionally. While incident/start validates against a whitelist of scenario IDs, the SCENARIO_AGENT_MAP is also consumed by agent.js route handlers (e.g. approve-escalation) which do not re-validate the scenarioId from the stored incident. Adding a new scenario without updating the map silently removes credential enforcement for that entire scenario.
Vulnerable Code
function checkCredentialPermission(scenarioId, action) {
  const agentId = SCENARIO_AGENT_MAP[scenarioId];
  if (!agentId) return {
    permitted: true,   // ← fail-open, not fail-closed
    credential: null,
    reason: 'No agent mapping — default allow'
  };
  return isPermitted(agentId, action);
}
Impact
Any new scenario added to the playbook without a corresponding SCENARIO_AGENT_MAP entry bypasses credential enforcement. All critical actions execute without a delegation check.
Fix
Return { permitted: false, reason: 'No agent mapping — action blocked' } when the scenario has no mapped agent. Add a startup assertion that every scenario in SCENARIOS has a map entry.
Reproduce
# Add a new scenario "INC-004" to data/scenarios.js but NOT to SCENARIO_AGENT_MAP
# Then call checkCredentialPermission('INC-004', 'ENGAGE_BACKUP_CRANE')
node -e "
const { checkCredentialPermission } = require('./backend/middleware/checkPermission');
const result = checkCredentialPermission('INC-004', 'ENGAGE_BACKUP_CRANE');
console.log(result);  // { permitted: true, credential: null, reason: 'No agent mapping — default allow' }
"
BUG-006 Session Cookie Transmitted Without secure Flag Medium
Location
backend/server.js : 39–43
Description
The session cookie omits secure: true. When deployed behind a TLS terminator (nginx, AWS ALB), cookies will still be sent by the browser over HTTP if accessed via HTTP redirect — making them susceptible to network interception. The sameSite: 'lax' setting does not protect against passive eavesdropping on non-HTTPS connections.
Fix
cookie: {
  httpOnly: true,
  sameSite: 'lax',
  secure: process.env.NODE_ENV === 'production',  // add this
  maxAge: 7 * 24 * 60 * 60 * 1000
}

BUG-007 All Active Incidents Lost on Server Restart — Zero Persistence High
Location
backend/routes/incident.js : 15
Description
Incidents are stored exclusively in a module-level JavaScript Map (incidentStore). Any server restart, crash, or hot-reload (nodemon) wipes every active incident. Meanwhile, approval_records and audit_events are persisted to SQLite — so the DB accumulates orphaned records referencing incident IDs that no longer exist in memory. A frontend polling an in-progress incident after a restart receives a 404 Incident not found with no recovery path.
Vulnerable Code
const incidentStore = new Map(); // module-level — dies with the process
// Audit events are written to SQLite
// but incidentStore is never flushed to disk
Impact
Server restart during active recovery = incident disappears. Human operator who approved an escalation has no record of the pending approval in the live system. DB has orphaned audit/approval rows forever.
Fix
Add an incidents table to SQLite. Persist incident state on each step completion. On boot, re-hydrate in-memory store from DB rows with status not in (complete, cancelled).
Reproduce
# 1. Start an incident
INC=$(curl -s -X POST http://localhost:3001/api/incident/start \
  -H "Content-Type: application/json" \
  -d '{"scenarioId":"INC-003"}' | python3 -c "import sys,json; print(json.load(sys.stdin)['incidentId'])")
echo "Incident: $INC"

# 2. Restart the backend (Ctrl+C, then npm run dev)

# 3. Try to poll status — returns 404
curl -s http://localhost:3001/api/incident/status/$INC
BUG-008 Credential expiresInHours Has No Range Validation High
Location
backend/routes/credentials.js : 11
Description
The credential issuance endpoint accepts expiresInHours from the request body with only a default value of 24. No minimum (0 or negative) or maximum validation is applied. An authenticated authority can issue a credential that expires in -1 hours (already expired at issuance), making no action permissible, or in 1000000 hours (~114 years), creating a near-permanent credential that never requires renewal.
Vulnerable Code
const { agentId, permissions, expiresInHours = 24 } = req.body;
// No: if (expiresInHours < 1 || expiresInHours > 720) return error
const expiresAt = new Date(Date.now() + expiresInHours * 60 * 60 * 1000).toISOString();
Impact
Negative hours → expired credential at issuance, silently blocks all agent actions. Extremely large hours → permanent credential, violates least-privilege principle and compliance requirements.
Fix
Validate: if (typeof expiresInHours !== 'number' || expiresInHours < 1 || expiresInHours > 720) return 400
Reproduce (requires auth session)
# Login first, then:
curl -s -X POST http://localhost:3001/api/credentials/issue \

  --cookie "connect.sid=<your-session>" \

    "agentId": "phoenix-port-01",
    "permissions": ["HALT_BERTH_7_OPERATIONS"],

BUG-009 Telemetry Update Formula Compounds — Metrics Overshoot Target Values Medium
Location
backend/agent/reasoningEngine.js : 183–184
Description
The telemetry interpolation formula uses completedCount * stepImpact * 0.7 as a multiplier on the remaining gap — but completedCount is the absolute step count, not a fractional progress. As steps accumulate, the multiplier grows unboundedly (step 5 = multiplier 0.98, step 6 = multiplier 1.176 > 1.0), causing metrics to overshoot their target values. For example, coolant flow can exceed its target of 48 L/min and read 54 L/min after step 5.
Vulnerable Code
const stepImpact = 0.28;
updated[key] = current + (target - current) * (completedCount * stepImpact * 0.7);
// completedCount=6: 6 * 0.28 * 0.7 = 1.176  → overshoots target
// The clamp below catches this but only for single-step scenarios
Impact
Telemetry charts display physically impossible values (negative pressure, flow rates above system capacity), misleading operators during recovery.
Fix
Use fractional progress: const frac = Math.min(1, completedCount / totalAuthorized); updated[key] = current + (target - current) * frac;
Reproduce
node -e "
const { computeUpdatedTelemetry } = require('./backend/agent/reasoningEngine');
const scenario = require('./backend/agent/playbook').getScenario('INC-001');
const initial  = { temperature: 94, pressure: 112, coolant_flow: 12, recovery_progress: 0 };
// Simulate 6 completed steps
const fakeSteps = Array(6).fill({ action: 'X' });
const result = computeUpdatedTelemetry(scenario, fakeSteps, initial);
console.log('coolant_flow target=48, got:', result.coolant_flow);  // may show > 48
console.log('temperature target=68, got:', result.temperature);    // may show < 68
"
BUG-010 Incident TTL Cleanup Uses Start Timestamp, Not Age — Evicts Fresh Incidents Medium
Location
backend/routes/incident.js : 19–28
Description
The TTL eviction loop compares the incident's absolute start timestamp to Date.now() - INCIDENT_TTL_MS. The variable is named age but actually holds the epoch milliseconds of the start time, not the age. The comparison is logically correct (start time older than 2h ago = evict) but is semantically misleading. More critically: if an incident is started at time T, and the server was running before midnight of the Unix epoch boundary (edge case), the comparison silently passes. Additionally, incidents stuck in blocked status waiting for human approval are evicted after 2 hours with no notification — the approval modal stays open in the frontend with no recovery.
Vulnerable Code
const cutoff = Date.now() - INCIDENT_TTL_MS;
for (const [id, inc] of incidentStore.entries()) {
  const age = new Date(inc.startTime).getTime();  // misleading name — this is startEpoch
  if (age < cutoff) {  // logically: startEpoch < (now - 2h)
    incidentStore.delete(id);  // evicts blocked incidents silently
  }
}
Impact
Incidents awaiting human approval silently evicted after 2h. Frontend shows stale approval modal with no server state. Human operator approves a ghost incident — returns 404.
Fix
Rename variable to startEpoch. Add explicit check: skip eviction if inc.status === 'blocked' (or extend TTL for blocked incidents to 24h). Emit a timeout audit event before eviction.
BUG-011 Login Has Zero Authentication — Any User Can Claim Any Authority Level High
Location
backend/routes/auth.js : 26–38
Description
The login endpoint accepts only a roleId string with no password, PIN, token, or any other secret. Any client who knows (or guesses) a valid authority ID string (harbor_master, datacenter_ops_manager, etc.) — all of which are returned by the public GET /api/auth/roles endpoint — can immediately claim LEVEL_3 authority and issue delegation credentials to any agent. There is no rate-limit on the login endpoint.
Vulnerable Code
router.post('/login', (req, res) => {
  const { roleId } = req.body;
  // No password. No PIN. No MFA. No secret.
  const authority = db.prepare('SELECT * FROM authorities WHERE id = ?').get(roleId);
  if (!authority) return res.status(404).json({ error: 'Role not found' });
  req.session.authorityId = authority.id;  // Instant LEVEL_3 access
  ...
});
Impact
Anyone can enumerate authority IDs from GET /api/auth/roles (public), then POST to /login with roleId: "harbor_master" to gain full LEVEL_3 access with zero credentials.
Fix
Add password field to authorities table, bcrypt hash comparison on login. Alternatively, add rate-limiting on login (max 5/min/IP) and document this as "demo-only" authentication clearly.
Reproduce

BUG-012 No Approval-Queue Persistence — Escalations Lost Across Browser Refresh Medium
Location
backend/routes/incident.js : 239–269 & frontend/src/App.jsx : 41–59
Description
When an incident is blocked pending human approval (pendingEscalation), that escalation lives only in the in-memory incident object. The frontend discovers it via polling and shows the approval modal. If the browser tab is closed and reopened, or the page is refreshed, the frontend re-polls the incident status and does recover the pendingEscalation object — but because there is no dedicated approval queue persisted to the database, a second admin logging in has no way to see what approvals are pending across all incidents. The document specifies an Approval Queue with states (Pending / Approved / Rejected / Expired) — only individual escalations in memory exist.
Impact
No central approval queue. Second operator cannot see pending approvals. No "Expired" state for approvals. Document Section 5 (Human Approval Center) is unimplemented.
Fix
Write pendingEscalation to the approval_records table with status='pending' when it is created. Update to 'approved'/'rejected' on resolution. Add GET /api/approvals/pending route.
BUG-013 After Rejection, Incident Remains Permanently Blocked — No Recovery Path High
Location
backend/routes/agent.js : 280–284
Description
When a human rejects an escalation via POST /api/agent/reject-escalation, the incident status is set to 'blocked' permanently. There is no mechanism to skip the rejected step and continue with subsequent playbook steps, nor to re-queue the same step for a second approval attempt. The document specifies dual-approval and emergency-override policies — neither is implemented. After rejection, the only option is to cancel the entire incident, losing all completed steps.
Vulnerable Code
incident.pendingEscalation = null;
incident.status = 'blocked';  // permanent — no path forward
incident.phase  = `Step rejected by ${rejectedBy}. Manual intervention required.`;
// No: executeNextStep() after skipping the rejected step
// No: retry queue, dual-approval fallback, emergency override
Impact
A single human rejection ends the recovery entirely. In a real plant, this could leave systems in a partially-recovered, dangerous intermediate state.
Fix
After rejection, mark the step as SKIPPED and call executeNextStep() to continue with subsequent authorized steps. Add an emergency-override policy that bypasses single-approval requirement.
Reproduce
# 1. Start INC-001 and wait for approval modal (RESTART_PRIMARY_COOLING)
# 2. Reject the escalation
curl -s -X POST http://localhost:3001/api/agent/reject-escalation \
  -H "Content-Type: application/json" \
  -d '{"incidentId":"<id>","action":"RESTART_PRIMARY_COOLING","rejectedBy":"Test"}'

# 3. Poll status — incident stuck in 'blocked', no further steps execute

Frontend Bugs

BUG-014 Dynamic Tailwind Class Names Purged From Production CSS Bundle High
Location
frontend/src/pages/LandingPage.jsx : 117–127 & LandingPage.jsx : 144–149
Description
Tailwind CSS uses static analysis at build time to find class names. Dynamic class construction using template literals breaks this: `bg-${accent}-500/10`, `hover:border-${accent}-500/40`, `text-${accent}-400`, and `hover:border-${s.color}-500/40` are never included in the compiled CSS bundle. In development, Vite's JIT may generate them on-demand, but in npm run build production output they are silently stripped. All six feature cards and the architecture flow steps render without their colored backgrounds, borders, and icons.
Broken Pattern (x3 components)
// FeatureCard — lines 117-127
`hover:border-${accent}-500/40 hover:bg-slate-800/80`   // never in bundle
`bg-${accent}-500/10 border border-${accent}-500/20`    // never in bundle
`text-${accent}-400`                                      // never in bundle

// ArchFlow — line 148
`hover:border-${s.color}-500/40`                           // never in bundle
Impact
Production build landing page shows all feature cards as plain grey boxes. Colored accents (blue for auth, purple for T3N, red for audit) are invisible. Major visual regression in the enterprise showcase page.
Fix
Replace dynamic classes with a lookup map of complete static class strings. Tailwind must see full class names as string literals. Example: const ACCENT_MAP = { blue: 'bg-blue-500/10 border-blue-500/20 text-blue-400', … }
Reproduce
# Build for production
cd frontend && npm run build

# Search the built CSS for any accent color classes
grep -c "bg-blue-500" dist/assets/*.css
# Returns 0 — the class is not in the bundle

# Serve and open browser — feature cards show no colour
npm run preview

Architecture Gaps vs. Document Specification

The following are features specified in the design document that are absent from the current implementation. They are not bugs in existing code but missing deliverables.

GAP-001 MCP Server Not Implemented (Document §8) Arch Gap
Document Requirement
Section 8 specifies a real MCP Server exposing tools: create_incident, halt_operations, dispatch_team, request_approval, get_audit_logs, verify_authorization, with endpoints /mcp/tools, /mcp/actions, /mcp/incidents, /mcp/audit supporting Claude MCP, Cursor, OpenAI Agents SDK, LangGraph, CrewAI.
Current State
Zero MCP endpoints exist. No /mcp/* routes in server.js. No MCP tool schema definitions. The platform cannot be used as an MCP server by any external AI framework.
Reproduce
curl http://localhost:3001/mcp/tools
# Returns: {"error":"Not found"} (404)
GAP-002 TypeScript Agent SDK Not Implemented (Document §9) Arch Gap
Document Requirement
Section 9 specifies a Phoenix TypeScript SDK with functions createAgent(), registerAgent(), authorizeAction(), requestApproval(), executeRecovery(), createAuditRecord(), plus Terminal 3 adapters: T3NService.createDID(), issueVC(), verifyDelegation(), createAuditVC().
Current State
No sdk/ directory exists. No TypeScript files anywhere in the project. The entire project is JavaScript, not TypeScript. No npm-publishable SDK package.
GAP-003 No WebSocket Support — Polling Used Instead (Document §12) Arch Gap
Document Requirement
Section 12 specifies real-time communication via REST + WebSocket + MCP. The Admin Portal (Section 2) requires "real-time updates".
Current State
Frontend polls every 1500ms with setInterval. No ws or socket.io dependency in either package.json. No WebSocket upgrade handler in server.js.
GAP-004 No Docker / Redis / BullMQ Infrastructure (Document §12) Arch Gap
Document Requirement
Section 12 Infrastructure: Docker, Redis, BullMQ for production deployment.
Current State
No Dockerfile, no docker-compose.yml, no Redis connection, no BullMQ queue. Backend uses in-memory state with no message broker.
Reproduce
ls /home/barath/Industrial_Recovery_Commander/
# No: Dockerfile, docker-compose.yml, .dockerignore
find . -name "*.yml" -not -path "*/node_modules/*"
# No docker-compose.yml found
GAP-005 Human Approval Center Has No Dedicated UI Page (Document §5) Arch Gap
Document Requirement
Section 5 specifies a Human Approval Center with a queue showing Pending / Approved / Rejected / Expired states, approval records with approver, timestamp, reason, incident ID, and policies: single approval, dual approval, emergency override.
Current State
Only a modal dialog (EscalationModal.jsx) appears during an active incident. No standalone approval queue page, no historical approval list, no dual-approval or emergency override policy engine.
GAP-006 Landing Page Stats Are All Hardcoded — Not Pulled From Real Data Arch Gap
Location
frontend/src/pages/LandingPage.jsx : 89–95
Description
The telemetry pulse bar shows "4 ACTIVE AGENTS", "12 INCIDENTS TODAY", "$2.4M COST SAVED", "847 ACTIONS VERIFIED BY T3N", "99.98% UPTIME". Full Reproduction Test Script

Save as reproduce-bugs.sh and run with bash reproduce-bugs.sh while the backend is running on port 3001.

#!/usr/bin/env bash
# Phoenix IRC — Bug Reproduction Test Suite
# Run: bash reproduce-bugs.sh
# Requires: backend running on localhost:3001, jq (apt install jq)

set -euo pipefail
BASE="http://localhost:3001"
PASS=0; FAIL=0
JAR=$(mktemp)

grn() { echo -e "\e[32m✓ PASS\e[0m $1"; ((PASS++)); }
red() { echo -e "\e[31m✗ FAIL\e[0m $1"; ((FAIL++)); }
blu() { echo -e "\e[34m───────────────────────────────────────\e[0m"; echo "  ▶ $1"; }

# ── BUG-001: Unauthenticated active credential endpoint ─────────────────────
blu "BUG-001: Unauth active credential"
STATUS=$(curl -s -o /dev/null -w "%{http_code}" "$BASE/api/credentials/active/phoenix-port-01")
[ "$STATUS" = "200" ] \
  && red "BUG-001 CONFIRMED: GET /api/credentials/active/:id returns $STATUS without auth" \
